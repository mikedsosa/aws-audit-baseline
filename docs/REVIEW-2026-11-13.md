## High

### H-1. Audit log versions can be deleted before the stated retention

Evidence:

- `terraform/variables.tf:89-98` sets `audit_noncurrent_version_days` default 30, allowed 7 through 90.
- `terraform/s3.tf:144-156` expires current audit objects after `audit_log_retention_days` (365) and noncurrent versions after `audit_noncurrent_version_days`.
- `terraform/locals.tf:140-149` denies `s3:DeleteObject` and `s3:DeleteObjectVersion`, but no statement denies an IAM caller who overwrites a log key with `aws:kms` (`terraform/locals.tf:106-125` only checks the encryption header).

Why it matters: in a versioning-enabled bucket, an overwrite makes the original version noncurrent. `NoncurrentVersionExpiration` then permanently deletes it, and a bucket policy cannot stop a lifecycle deletion [S1]. So an overwritten log could be gone after 30 days, even though the docs state 365 days of retention.

Fix:

- `audit_noncurrent_version_days` default is now 365, allowed 365 through 3650 (`terraform/variables.tf`).
- A `precondition` on `aws_s3_bucket_lifecycle_configuration.audit_logs` fails the plan when noncurrent days are below `audit_log_retention_days` (`terraform/s3.tf`). A local plan with `audit_log_retention_days=730` and `audit_noncurrent_version_days=400` failed with "Resource precondition failed".
- `S3-LIFE-001` now needs every audit noncurrent expiration to be 365 through 3650 days.
- New rule `S3-RET-001` (see H-2).

Tests: `test_short_noncurrent_retention_fails`, `test_noncurrent_shorter_than_current_fails`, `test_unknown_noncurrent_days_is_unknown` in `tests/test_review_gaps.py`. The `b2085aa` offline plan now gets `fail` on `S3-RET-001` and `S3-LIFE-001`.

### H-2. The lifecycle check can be bypassed with a second rule

Evidence: `src/aws_baseline_evidence/rules.py:742-753` uses `any(...)` over the days found in all rules. `rules.py:726` reads only `expiration.days`, so an expiration by date is ignored.

Why it matters: a plan can keep the 365 day rule and add an enabled rule, for example with a `cloudtrail/AWSLogs/` prefix filter, that expires log objects after 1 day. `S3-LIFE-001` still passes. When several rules match, S3 applies them by precedence, with permanent deletion first [S1].

Fix: new rule `S3-RET-001` checks every enabled audit lifecycle rule:

- current-version expiration days must be at least 365 (`AUDIT_RETENTION_FLOOR_DAYS` in `catalog.py`);
- noncurrent expiration days must be at least 365 and not less than the current-version days;
- an expiration by date fails, because the checker cannot compare a date to a retention period;
- disabled rules are skipped by `S3-RET-001`. `S3-LIFE-001` still fails any rule that is not `Enabled`.

The workload noncurrent check in `S3-LIFE-001` now also uses every rule rather than any rule.

Tests: `test_extra_prefix_rule_that_expires_logs_early_fails`, `test_expiration_by_date_fails`, `test_disabled_short_rule_does_not_fail_retention`.

### H-3. Audit logs are not immutable

Evidence: `terraform/s3.tf:86` sets `object_lock_enabled = false`. The delete protection is a bucket policy statement (`terraform/locals.tf:140-149`) and a lifecycle rule (`terraform/s3.tf:130-160`). A principal who can call `PutBucketPolicy` or `PutLifecycleConfiguration` can remove the deny or shorten retention. Lifecycle ignores bucket policy denies [S1].

What Object Lock changes, per AWS:

- In compliance mode no user, including the root user, can overwrite or delete a protected version or shorten its retention; the only way to delete it early is to delete the account [S2].
- In governance mode, a user with `s3:BypassGovernanceRetention` who sends `x-amz-bypass-governance-retention:true` can override it [S2].
- Lifecycle cannot delete a locked version [S3].
- After Object Lock is enabled on a bucket, it cannot be disabled and versioning cannot be suspended [S3].
- AWS's Security Reference Architecture names Object Lock, versioning, and lifecycle as the controls that support log availability [S20].

Fix (partial):

- New variable `audit_object_lock_mode`, values `OFF` (default), `GOVERNANCE`, or `COMPLIANCE`.
- When it is not `OFF`, the audit bucket is created with Object Lock and `aws_s3_bucket_object_lock_configuration.audit_logs` sets a default retention of `audit_log_retention_days` in that mode.
- `S3-LOCK-001` now passes an audit bucket only when Object Lock is either explicitly off (reported as "not an immutability control") or on with exactly one default retention rule in `GOVERNANCE` or `COMPLIANCE` mode for at least 365 days. A lock configuration on a bucket created with `object_lock_enabled = false` fails. The workload bucket must still have Object Lock off.
- A local plan with `audit_object_lock_mode=GOVERNANCE` planned 25 resources and scored 47 pass, 0 fail, 6 unknown.

Why the default stays `OFF`: Object Lock cannot be turned off later, and a COMPLIANCE retention of 365 days cannot be shortened by anyone [S2, S3]. That is a one-way decision for whoever applies this stack. CloudTrail delivery into a locked bucket was not tested, because nothing was applied. Mike should choose the default.

Tests: `test_object_lock_with_retention_passes` (both modes), `test_object_lock_short_retention_fails`, `test_object_lock_years_count_toward_floor`, `test_object_lock_bad_mode_fails`, `test_object_lock_without_default_retention_fails`, `test_object_lock_config_on_unlocked_bucket_fails`, `test_workload_object_lock_still_must_be_off`, plus the committed fixture `tests/fixtures/synthetic-object-lock.json`.

## Medium

### M-1. No account-level S3 Block Public Access

Evidence: there was no `aws_s3_account_public_access_block` in `terraform/` at `b2085aa`. `docs/LIMITS.md` listed this as a known gap.

AWS recommends turning on all four settings for the account, because a user who can change a bucket policy can insert a policy that disables the bucket-level setting; with the account setting on, S3 blocks public policies even then [S4]. Account settings apply to all Regions [S4].

Fix: `terraform/account.tf` adds `aws_s3_account_public_access_block.account` with all four settings true and `account_id = var.account_id`. New rule `S3-ACCT-BPA-001` fails if the block is missing, if there is more than one, if any flag is not true, or if `account_id` is not the plan's account.

Caveats, also in the Terraform comment:

- The setting covers every bucket in the account, not only this stack's.
- Account-level `PutPublicAccessBlock` and `DeletePublicAccessBlock` return Access Denied when the account is managed by an organization-level S3 policy [S5]. In that case remove this resource and rely on the organization policy.
- Destroying this resource is expected to remove the account setting. That was not tested.
- The provider docs say only one such configuration per account is supported [S21].

Tests: `test_missing_account_public_access_block_fails`, `test_account_public_access_flag_false_fails` (four cases), `test_account_public_access_other_account_fails`, `test_account_public_access_unknown_flag_is_unknown`, `test_two_account_public_access_blocks_fail`.

### M-2. No S3 data events

Evidence: `terraform/cloudtrail.tf:12-15` has only a management event selector. `src/aws_baseline_evidence/rules.py:1140-1145` failed `CT-DATA-001` if `data_resource` was not empty, so the checker penalized adding object-level logging.

Trails do not log data events by default, and S3 object-level calls such as `GetObject` and `PutObject` are data events [S6]. CIS AWS Foundations Benchmark v5.0.0 3.8 and 3.9 cover object-level write and read logging for S3 [S13].

Fix: the trail's event selector now has one `data_resource` of type `AWS::S3::Object` with the value `arn:<partition>:s3:::<workload bucket>/`. `CT-DATA-001` now requires exactly that one value. It fails if the audit bucket is included, because a trail that logs data events on its own log bucket logs its own deliveries [S6], and it fails on an account-wide value such as `arn:aws:s3`.

Cost: CloudTrail lists data events delivered to S3 at $0.10 per 100,000 events [S7]. That is a list price, not a measured bill. Nothing was deployed.

Tests: `test_no_data_events_now_fails`, `test_audit_bucket_as_data_resource_fails`, `test_all_buckets_data_resource_fails`, `test_wrong_data_resource_type_fails`, `test_unknown_data_values_are_unknown`. `tests/test_generated_plan.py::test_generated_plan_has_review_gap_fixes` checks the offline plan.

### M-3. Workload key grant is wider than S3 needs

Evidence: `terraform/locals.tf:171-177` granted `kms:Encrypt`, `kms:Decrypt`, `kms:ReEncrypt*`, `kms:GenerateDataKey`, and `kms:DescribeKey`. `rules.py:55-63` required exactly that set.

The S3 SSE-KMS page lists `kms:GenerateDataKey` for `PutObject`, `kms:Decrypt` for downloads, and both for multipart upload [S8].

Fix: the grant is now `kms:Decrypt` and `kms:GenerateDataKey`, still conditioned on `kms:ViaService` and the bucket encryption context. `KMS-POL-001` expects that set. New rule `KMS-SCOPE-001` fails any non-root Allow statement on either key that grants an action outside `kms:Decrypt`, `kms:DescribeKey`, `kms:GenerateDataKey`, `kms:GenerateDataKey*`, that names a wildcard principal, or that has no condition. The one exception is the documented CloudTrail decrypt statement (L-4).

Tests: `test_workload_key_encrypt_and_reencrypt_fail`, `test_extra_wildcard_principal_key_statement_fails`, `test_unconditioned_auditor_decrypt_fails_scope`, `test_admin_action_for_auditor_fails_scope`. The `b2085aa` plan now fails `KMS-SCOPE-001` on the workload key.

Not verified: that S3 never needs `kms:DescribeKey` from the workload role on this key. If an apply shows otherwise, add it back; `KMS-SCOPE-001` allows it.

### M-4. Auditor decrypt is not limited to S3

Evidence: `terraform/locals.tf:241-254` allowed the auditor role `kms:Decrypt` on the audit key with only a `Null` check on the CloudTrail encryption context. The auditor could call KMS directly with any ciphertext that carries that context.

Fix: the statement now also requires `kms:ViaService` = `s3.<region>.amazonaws.com`. That key limits use of a KMS key to requests from the named service [S10]. `KMS-POL-001` requires it.

Test: `test_auditor_decrypt_without_via_service_fails_policy`.

Not verified: any log tool that decrypts outside S3 would now be denied. `aws cloudtrail validate-logs` was not run.

### M-5. Workload uploads are not pinned to the workload key (deferred)

Evidence: `terraform/locals.tf:44-55` denies `PutObject` unless `s3:x-amz-server-side-encryption` is `aws:kms`. It does not check `s3:x-amz-server-side-encryption-aws-kms-key-id`.

The S3 SSE-KMS page says a request that sends `aws:kms` without a key id header is treated as a request for the AWS managed key, and it documents the key-id condition for requiring a particular key [S8].

Why deferred: the key ARN is known only after apply, so a key-id deny would add another unknown to the offline plan, and how this interacts with the bucket's default key was not tested. Recommended change before any apply: add a deny on `PutObject` when `s3:x-amz-server-side-encryption-aws-kms-key-id` is not the workload key ARN, and a checker rule for it.

### M-6. Account-root `kms:*` delegates to IAM (deferred)

Evidence: `terraform/locals.tf:156-164` and `192-200`.

The default key policy gives the account `kms:*` so IAM policies can grant key access, and AWS says this reduces the risk of the key becoming unmanageable [S9]. Any IAM principal in the account with a broad KMS policy can therefore use or administer both keys, and the checker cannot see those policies.

Why deferred: removing the root statement without named key administrators risks an unmanageable key [S9]. `KMS-SCOPE-001` skips the root statement on purpose and says so in its pass reason. `other-iam-in-the-account` stays in `not_assessed`.

### M-7. IAM callers can overwrite audit objects (deferred)

Evidence: `terraform/locals.tf:106-125` denies non-CloudTrail uploads only when the header is not `aws:kms`.

After H-1, an overwritten log keeps its old version for at least 365 days as noncurrent, so the overwrite is recoverable within retention, but it is not blocked.

Why deferred: a deny on all non-CloudTrail `PutObject` would depend on `aws:PrincipalServiceName` being present on CloudTrail's delivery requests. That was not verified, and getting it wrong would stop log delivery. Added `audit-bucket-overwrite-by-iam` to `not_assessed`.

## Low

### L-1. Single-account trail (deferred)

Evidence: `terraform/cloudtrail.tf:10` sets `is_organization_trail = false`, and `CT-FLAG-001` requires that.

An organization trail must be created from the management account or a delegated administrator. Users in member accounts cannot delete it, turn logging off, or change what it logs [S11]. That is stronger tamper resistance than this stack's trail, which any principal in the account with CloudTrail write permissions can stop.

Why deferred: this repository models one account. Added `organization-trail-scope` to `not_assessed`. IAM-TAMPER-001 (L-3) only covers the two baseline roles.

### L-2. No IAM Access Analyzer (deferred)

CIS v5.0.0 1.19 and Security Hub IAM.28 ask for an external access analyzer [S13, S15]. The external access analyzer is provided at no additional charge [S17]. Analyzers are per Region [S16], and the quota is one account-level analyzer per analyzer type per account per Region [S18].

Why deferred: creating one here could collide with an analyzer the account already has, and it would need one per Region with resources. It belongs in account setup, not in this workload stack. The `not_assessed` text now says so.

### L-3. No independent tamper-action check

Evidence: `IAM-PERM-001` (`rules.py:1270-1478`) enforces exact allowlists, which is good, but there is no invariant that says what must never be granted.

Fix: new rule `IAM-TAMPER-001` fails if any Allow statement in a baseline role's inline policies matches, directly or by wildcard, an action in `TAMPER_ACTIONS` in `catalog.py`: stopping, deleting, or updating the trail, changing selectors, changing bucket policy, public access block, versioning, lifecycle, Object Lock or retention, bypassing governance retention, changing key policy, creating grants, disabling or scheduling deletion of a key, or changing the roles' own policies. Matching is case-insensitive. Deny statements are ignored.

Tests: `test_tamper_action_in_role_policy_fails` (five cases, including `s3:Put*`, `*`, and an upper-case action), `test_tamper_action_under_deny_is_not_a_finding`.

### L-4. CloudTrail decrypt without `aws:SourceArn` (deferred)

Evidence: `terraform/locals.tf:232-240`.

The CloudTrail KMS page publishes this statement without a condition, and says `kms:Decrypt` is required when a trail with SSE-KMS uses a bucket with an S3 Bucket Key [S12]. Adding a condition that page does not show could break delivery. `KMS-SCOPE-001` allows exactly this statement and nothing wider.

### L-5. MFA Delete is off (deferred)

The CloudTrail security best-practices page says MFA Delete cannot be used with lifecycle configurations [S14]. This stack depends on lifecycle, so MFA Delete stays off. Object Lock (H-3) is the alternative.

### L-6. No server access logs for the CloudTrail bucket (deferred)

CIS v5.0.0 3.4 and Security Hub CloudTrail.7 cover S3 access logging on the CloudTrail bucket [S13]. The S3 SSE-KMS page says a server access logging destination bucket must use SSE-S3, not SSE-KMS [S8]. That means a third bucket with a different encryption setting. Left out of this change set; `s3-server-access-logging` stays in `not_assessed`.

### L-7. Alias ARN instead of key ARN (deferred)

Evidence: `terraform/s3.tf:41` and `123`, `terraform/cloudtrail.tf:5`.

The S3 SSE-KMS page recommends a fully qualified key ARN, because an alias is resolved in the requester's account [S8]. Here the requester and the key are in the same account, so this is not a known break. `S3-ENC-001` and `CT-DEST-001` would need to change together, so it is left as a note.

## Info

### I-1. Trail read APIs on `Resource "*"`

Evidence: `terraform/locals.tf:377-385`, and `docs/LIMITS.md` said resource-level support had not been re-read.

AWS's service reference JSON for CloudTrail lists no resource types for `LookupEvents`, `DescribeTrails`, and `ListTrails`, and lists the `trail` resource for `GetTrail`, `GetTrailStatus`, and `GetEventSelectors` [S19]. So `Resource "*"` is required for the first three, and the policy already scopes the other three to the trail ARN.
